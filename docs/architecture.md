# Wardrobe — архитектура

Статус: baseline v0.1

## 1. Основные решения

- Модульный Go-монолит вместо микросервисов.
- PostgreSQL как серверный источник истины.
- SQLite как основной источник данных для мобильного UI.
- Веб-клиент работает онлайн через тот же backend.
- REST/JSON с префиксом /api/v1.
- OpenAPI является контрактом для генерации TypeScript-типов.
- Фотографии хранятся вне PostgreSQL.
- Собственный узкий sync-протокол только для доменных сущностей.
- Docker Compose и один экземпляр backend в MVP.
- S3, Redis, Kafka и Kubernetes не требуются.

Все изменения веба и мобильных устройств проходят через общие domain services. Нельзя менять синхронизируемые сущности напрямую из HTTP handlers, минуя версии и журнал изменений.

## 2.1. Единый write path

Не должно быть отдельных независимых реализаций:

```text
items.Update()      — для веба
sync.UpdateItem()   — для мобильной синхронизации
```

Веб-CRUD и sync push используют одни и те же доменные операции:

- проверку владельца;
- проверку `base_version`;
- валидацию;
- изменение сущности;
- увеличение `version`;
- добавление записи в `sync_changes`.

Sync push дополнительно обрабатывает `mutation_id` и `processed_mutations`.

Каждое изменение выполняется в одной транзакции PostgreSQL:

```text
BEGIN

1. Заблокировать user_sync_state пользователя.
2. Для sync push:
   - проверить mutation_id;
   - проверить request_hash;
   - обработать повторную доставку.
3. Проверить существование сущности и владельца.
4. Проверить base_version.
5. Проверить доменные инварианты.
6. Изменить сущность и увеличить её version.
7. Увеличить last_seq пользователя.
8. Добавить полный snapshot или tombstone в sync_changes.
9. Для sync push сохранить processed_mutations.

COMMIT
```

## 2.2. Change journal

Пакет `changejournal` отвечает за запись в `sync_changes`:

- блокировка `user_sync_state` через `SELECT FOR UPDATE`;
- выделение следующего `seq`;
- запись полного snapshot или tombstone;
- запрет записи без владельца.

`changejournal` не импортирует `categories`, `items` или `photos`.

## 2.3. Владелец

Auth middleware только устанавливает аутентифицированного пользователя.

Проверка владельца выполняется в service/repository:

- чужой ресурс в path → `404 Not Found`;
- невалидная ссылка на категорию → `422 invalid_category`;
- `user_id` никогда не принимается из клиентского payload.

## 4. Backend

Рекомендуемый стек:

- Go net/http и chi.
- pgx/v5 для соединения с PostgreSQL.
- sqlc для типизированных запросов.
- goose для миграций.
- slog для структурных логов.
- Аргон2id для паролей.
- OpenAPI 3 для HTTP-контракта.

Слои:

1. HTTP handler: декодирование, аутентификация, статус ответа.
2. Application/domain service: транзакции и бизнес-инварианты.
3. Repository: SQL и отображение типов.
4. Infrastructure: PostgreSQL, файлы, clock, UUID и logging.

Правила:

- Handler не содержит SQL.
- Repository не принимает решений о конфликтах.
- Сервис синхронизации использует доменные валидации.
- user_id берётся из серверной сессии, а не из JSON.
- Каждая SQL-операция ограничена контекстом и timeout.

## 5. Аутентификация и регистрация

### Приглашения

Токен приглашения:

- Содержит не менее 256 бит случайности.
- Передаётся в URL в base64url.
- В базе сохраняется SHA-256 хеш.
- Имеет expires_at и used_at.
- Может быть привязан к нормализованному email.

Регистрация выполняется в транзакции:

1. Заблокировать приглашение FOR UPDATE.
2. Проверить срок, отзыв и использование.
3. Проверить email и уникальность пользователя.
4. Создать пользователя.
5. Создать user_sync_state.
6. Скопировать базовые категории.
7. Записать изменения категорий в sync journal.
8. Пометить приглашение использованным.
9. Зафиксировать транзакцию.

### Сессии

- Случайный opaque token не является JWT.
- В БД хранится только его хеш.
- Сессия имеет expires_at, revoked_at и last_used_at.
- Web transport: HttpOnly Secure cookie.
- Mobile transport: Authorization Bearer.
- Logout отзывает серверную сессию.
- При смене пароля или блокировке пользователя сессии могут быть отозваны массово.

Веб защищается от CSRF сочетанием SameSite cookie, Origin/Fetch Metadata проверок и CSRF token для unsafe methods.

## 6. Категории

Базовый справочник является версионируемым шаблоном в Go-коде или в embedded JSON.

Копирование шаблона выбрано вместо глобальных read-only категорий, потому что:

- Не требуется объединять два разных источника категорий при синхронизации.
- Пользовательские изменения не затрагивают других пользователей.
- Локальная SQLite-модель остаётся однородной.
- Будущее изменение шаблона не меняет существующие гардеробы.

Проверка цикла выполняется в транзакции рекурсивным CTE. Перемещение и проверка не должны выполняться как независимые незащищённые запросы.

## 7. Вещи и деньги

purchase_price имеет тип BIGINT.

Семантика:

- Целые основные единицы валюты.
- Без копеек, центов и дробной части.
- Ноль допускается.
- NULL означает отсутствие данных о цене.
- price_currency заполняется вместе с ценой.
- RUB является значением формы по умолчанию, а не принудительным значением БД.

В Go используется *int64 или отдельный Money-тип. JSON-представление цены — строка. В TypeScript значение остаётся строкой до момента форматирования.

Каталог валют находится в общем контракте клиентов. Список ISO-кодов можно расширять без изменения существующих записей.

## 8. Места хранения

Отдельной таблицы мест хранения нет.

Мобильные подсказки:

- SELECT DISTINCT по локальным непустым значениям.
- Поиск без учёта регистра.
- Приоритет частым и недавно использованным значениям.

Веб-подсказки:

- Только записи текущего пользователя.
- Лимит по умолчанию 10.
- Группировка нормализованного значения.
- Сохранение исходного регистра у вещи.

## 9. Фотографии

PhotoStorage имеет минимальный интерфейс:

- Сохранить содержимое по ключу.
- Открыть содержимое.
- Удалить содержимое.
- Проверить существование.

LocalPhotoStorage использует ключи вида:

    users/<user_uuid>/items/<item_uuid>/<photo_uuid>/original.jpg
    users/<user_uuid>/items/<item_uuid>/<photo_uuid>/thumbnail.jpg

Ключи формируются сервером. Оригинальное имя файла не участвует в пути.

Upload:

1. Проверить владельца и лимит фотографий.
2. Записать upload во временный файл с ограничением размера.
3. Определить формат по содержимому.
4. Декодировать с защитой от чрезмерных размеров.
5. Сформировать оригинал и миниатюру.
6. Сохранить файлы.
7. В транзакции обновить metadata и записать sync change.
8. Очистить временные файлы.

Возможные осиротевшие файлы удаляются периодической reconciliation-задачей. В MVP задача может запускаться внутри одного backend.

Скачивание:

- Backend сначала проверяет user_id по metadata.
- Файл отдаётся через API или внутренний X-Accel/X-Sendfile-механизм при появлении необходимости.
- Прямой листинг каталога отключён.
- Мобильный клиент кэширует thumbnail и original раздельно.

## 10. Согласованность и журнал изменений

Каждая синхронизируемая сущность имеет:

- UUID.
- user_id.
- version.
- created_at и updated_at.
- deleted_at, если поддерживается удаление.

Для каждого пользователя существует last_seq.

При изменении сущности в одной транзакции:

1. Проверяется владелец.
2. Проверяется base_version.
3. Обновляются данные и version.
4. Блокируется user_sync_state.
5. Увеличивается last_seq.
6. В sync_changes записывается полный snapshot или tombstone.
7. Фиксируется транзакция.

Порядок блокировок должен быть единым во всех сервисах. Рекомендуемый упрощённый вариант для MVP: сначала блокировать sync-state пользователя, затем применять доменное изменение. Это сериализует записи одного пользователя, чего достаточно при ожидаемых объёмах.

updated_at не используется как курсор синхронизации.

## 11. Мобильная архитектура

Модули:

- Local DB: SQLite schema и миграции.
- Repositories: единственный способ чтения и изменения локальных данных для UI.
- Outbox: надёжная очередь доменных операций.
- Sync Engine: push, pull, retry и compaction.
- Photo Manager: локальные файлы и очередь загрузки.
- Auth Store: токен в Secure Store.
- UI: React Native screens и components.

Инвариант:

    Локальное сохранение считается успешным только после commit SQLite,
    содержащего одновременно данные сущности и необходимые outbox-записи.

Sync Engine запускается в одном экземпляре. Повторные триггеры не создают параллельные push/pull-циклы.

## 12. Веб-клиент

- HTML используется для семантической разметки.
- CSS отвечает за adaptive layout.
- TypeScript управляет состоянием и API-запросами.
- UI-фреймворк не используется.
- Vite нужен только на этапе сборки.
- Маршрутизация может быть реализована небольшим History API router.
- /api и служебные пути не попадают под SPA fallback.
- Неизвестный API path возвращает JSON 404, а не index.html.

## 13. Docker и окружение

Production-сервисы:

- caddy: HTTPS и reverse proxy.
- api: backend, веб-файлы и CLI.
- postgres: PostgreSQL.

Volumes:

- postgres-data.
- photo-storage.
- caddy-data.
- caddy-config.

Основные переменные:

- DATABASE_URL.
- HTTP_ADDR.
- PUBLIC_BASE_URL.
- PHOTO_STORAGE_DIR.
- SESSION_COOKIE_SECURE.
- SESSION_TTL.
- INVITATION_DEFAULT_TTL.
- MAX_UPLOAD_BYTES.
- LOG_LEVEL.
- BACKUP_* для внешних backup-скриптов.

Секреты не сохраняются в репозитории. Миграции запускаются отдельной командой до запуска новой версии API.

## 14. Наблюдаемость и backup

Логи:

- JSON в production.
- request_id.
- user_id только как внутренний идентификатор.
- route, status и duration.
- Без токенов, паролей, тел запросов и signed URLs.

Метрики можно добавить после MVP. Минимально необходимы healthchecks и алерты на диск, ошибки контейнера и неудачные backups.

Backup:

- Регулярный pg_dump или физический backup PostgreSQL.
- Копирование photo-storage.
- Шифрование внешней копии.
- Проверка сроков хранения.
- Периодическое восстановление на чистой установке.
- После восстановления — сопоставление metadata и файлов.

## 16. Возможное развитие

Не требует смены архитектуры:

- S3 через вторую реализацию PhotoStorage.
- Вынос обработки изображений в worker.
- Сжатие старого sync journal после добавления device cursors.
- Outfits и история носки новыми модулями.
- Подписанные URL при переходе к объектному хранилищу.

Преждевременно в MVP:

- Горизонтальное масштабирование API.
- Распределённые очереди.
- CRDT.
- Микросервисы.
- Общая offline-реализация для веба.
