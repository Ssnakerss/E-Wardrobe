# Backend Implementation Plan — Wardrobe

**Дата обновления:** 2026-11-24  
**Цель:** реализация production-ready backend для MVP Wardrobe  
**Архитектура:** Go-монолит с модульной структурой, PostgreSQL, локальное файловое хранилище фотографий  
**Особенность:** offline-first синхронизация закладывается в доменную модель с первых этапов, а не добавляется после завершения CRUD

## 2. Ключевые архитектурные инварианты

Эти правила обязательны на всех этапах.

### 2.1. Единый путь изменения доменных данных

Не должно быть отдельных независимых реализаций:

```text
items.Update()      — для веба
sync.UpdateItem()   — для мобильной синхронизации
```

Веб-CRUD и sync push используют одни и те же доменные операции:

- проверку владельца;
- проверку `base_version`;
- валидацию;
- изменение сущности;
- увеличение `version`;
- добавление записи в `sync_changes`.

Sync push дополнительно обрабатывает `mutation_id` и `processed_mutations`.

### 2.2. Атомарность записи

Каждое изменение категории, вещи или metadata фотографии выполняется в одной транзакции PostgreSQL:

```text
BEGIN

1. Заблокировать user_sync_state пользователя.
2. Для sync push:
   - проверить mutation_id;
   - проверить request_hash;
   - обработать повторную доставку.
3. Проверить существование сущности и владельца.
4. Проверить base_version.
5. Проверить доменные инварианты.
6. Изменить сущность и увеличить её version.
7. Увеличить last_seq пользователя.
8. Добавить полный snapshot или tombstone в sync_changes.
9. Для sync push сохранить processed_mutations.

COMMIT
```

Недопустимо разносить изменение сущности, журнал и результат mutation по разным транзакциям.

### 2.3. Сериализация доменных записей пользователя

Все записи в `categories`, `items`, `item_photos` и связанный журнал изменений сериализуются через блокировку соответствующей строки `user_sync_state`.

Для ожидаемых объёмов это даёт:

- монотонный и непрерывный порядок выделения `seq`;
- предсказуемый порядок commit;
- защиту от конкурентного создания циклов категорий;
- упрощение проверки версий;
- отсутствие необходимости в распределённых блокировках.

Блокировки применяются в едином порядке: сначала `user_sync_state`, затем доменные сущности.

### 2.4. Веб-изменения обязаны попадать в sync journal

Любая операция через веб-CRUD должна быть видна мобильным клиентам через:

```text
GET /api/v1/sync/pull
```

Прямая запись в доменные таблицы из HTTP handlers или сторонних служебных функций запрещена.

### 2.5. Владелец проверяется в доменном слое

Auth middleware только устанавливает аутентифицированного пользователя.

Проверка владельца выполняется в service/repository:

- чужой ресурс в path обрабатывается как `404 Not Found`;
- это не раскрывает существование чужого UUID;
- невалидная ссылка на категорию при создании или обновлении вещи возвращает `422 invalid_category`;
- `user_id` никогда не принимается из клиентского payload.

### Правила организации кода

- Единственный каталог generated sqlc-кода: `internal/platform/database/sqlc`.
- Миграции находятся только в корневом `migrations/`; symlink и копии не используются.
- Один multi-stage `Dockerfile` собирает оба бинарника: `server` и `wardrobe`.
- В runtime image оба бинарника доступны, нужный выбирается через `command`.
- HTTP handlers разделяются по доменам, общий `handler.go` не создаётся.
- Repository не открывает собственные транзакции.
- Application service управляет транзакцией и передаёт transaction-bound repositories.
- `changejournal` не импортирует `categories`, `items` или `photos`.
- `sync` вызывает доменные mutation appliers через явные интерфейсы; доменные модули не импортируют HTTP sync service.

## 4. Общие правила реализации

### API и ошибки

- API prefix: `/api/v1`.
- Единый JSON error response:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Request validation failed",
    "details": {}
  }
}
```

- Для JSON используется строгое декодирование:
  - запрет неизвестных полей;
  - запрет нескольких JSON-значений в одном теле;
  - ограничение размера тела;
  - проверка `Content-Type`.
- `PATCH` различает:
  - поле отсутствует — не изменять;
  - поле равно `null` — очистить nullable-поле;
  - значение передано — установить его.
- Для этого используется typed optional/update-модель, а не только `*string`.

### Версии

- `base_version` для `PATCH` передаётся в теле запроса согласно OpenAPI.
- `base_version` для `DELETE` передаётся в query.
- При несовпадении версии возвращается `409 version_conflict`.
- Два параллельных update с одной `base_version` не могут оба успешно завершиться.

### Данные

- Цена: `*int64` в Go, целое число в основных единицах валюты.
- В JSON цена передаётся строкой, например `"12990"`.
- Дробная и отрицательная цена отклоняются.
- Цена и валюта указываются только вместе.
- Время: `time.Time`, PostgreSQL `timestamptz`, UTC.
- UUID: `github.com/google/uuid`.
- Статусы: typed string enums, валидация в Go и ограничения в БД.

## Этап 1. Identity, приглашения, сессии и recovery

**Цель:** полностью закрытый контур регистрации по приглашению и аутентификации.

### Задачи

### Приглашения

- CLI:
  - `invite create`;
  - `invite revoke`.
- Токен содержит не менее 256 бит случайности.
- В БД сохраняется только SHA-256 хеш.
- Поддерживаются email, expiration, revoke и одноразовое использование.
- API:
  - `POST /api/v1/auth/invitations/validate`;
  - `POST /api/v1/auth/register`.

### Пользователи и сессии

- Регистрация, login, logout, `auth/me`.
- Argon2id для паролей.
- Opaque session tokens через `crypto/rand`.
- В БД хранятся только хеши токенов.
- Web transport:
  - `HttpOnly`;
  - `Secure`;
  - подходящий `SameSite`.
- Mobile transport:
  - `Authorization: Bearer`.
- `last_used_at` обновляется с порогом, а не при каждом запросе.
- Истёкшие и отозванные сессии отклоняются.

При регистрации на этом этапе создаются:

- пользователь;
- `user_sync_state`;
- сессия.

Bootstrap категорий подключается на этапе 2.

### CSRF и CORS

- CSRF проверяется для cookie-authenticated unsafe requests.
- Logout веб-клиента также защищён CSRF.
- Bearer-запросы мобильного приложения CSRF-проверки не требуют.
- Дополнительно проверяются `Origin` и/или Fetch Metadata.
- Same-origin production не требует открытого CORS.
- В development используется только явный allowlist origin.
- `Access-Control-Allow-Origin: *` не применяется.

### Recovery

CLI создаёт одноразовую recovery-ссылку.

Добавляются endpoints:

```text
POST /api/v1/auth/recovery/validate
POST /api/v1/auth/recovery/complete
```

При успешном восстановлении в одной транзакции:

- токен погашается;
- обновляется пароль;
- существующие сессии пользователя отзываются.

### Rate limiting

Ограничиваются:

- login;
- register;
- invitation validate;
- recovery validate/complete.

Для одного backend-инстанса допустим in-memory limiter с очисткой старых записей. Доверие к proxy headers настраивается явно через список trusted proxies.

### Обязательные тесты

- Валидная регистрация и вход.
- Просроченное, отозванное и использованное приглашение.
- Два параллельных запроса на одно приглашение: только один успешен.
- Параллельная регистрация одинакового email.
- Повторное использование recovery-токена.
- Отзыв сессий после recovery.
- CSRF для cookie и отсутствие CSRF-требования для Bearer.
- Rate limiting без блокировки локальных тестов.
- В логах отсутствуют пароли и токены.

## Этап 2. Change journal, категории и первый sync-срез

**Цель:** реализовать правильный доменный write path и проверить его на категориях до разработки остальных сущностей.

### Задачи

### Change journal

Реализовать `changejournal`:

- блокировку `user_sync_state`;
- выделение следующего `seq`;
- запись полного snapshot или tombstone;
- получение изменений для pull;
- запрет записи без владельца.

Версия новой сущности равна `1`.

### Категории

- CRUD категорий.
- Flat list для построения дерева на клиенте.
- Перемещение категории.
- Проверка циклов рекурсивным CTE.
- Проверки выполняются внутри общей сериализованной транзакции.
- Soft delete и архивирование.
- Запрет удаления используемой категории или категории с детьми.
- Все операции увеличивают `version` и создают journal entry.

### Bootstrap базового шаблона

Bootstrap подключается к регистрации.

В одной транзакции:

- погашается приглашение;
- создаётся пользователь;
- создаётся `user_sync_state`;
- копируются категории;
- каждая категория получает `version = 1`;
- для каждой категории создаётся sync change.

Повторная попытка регистрации не создаёт частично заполненный гардероб.

### Первый вертикальный sync-срез

Для категорий реализовать:

- typed create applier;
- `POST /api/v1/sync/push`;
- `GET /api/v1/sync/pull`;
- `processed_mutations`;
- canonical `request_hash`;
- успешный retry как `duplicate`;
- отсутствие новых `version` и `seq` при повторе.

### Критерии готовности и тесты

- CRUD категорий работает через веб-API.
- Категория, созданная через веб, появляется в pull.
- При регистрации создаётся полный шаблон и его journal history.
- Повтор mutation не создаёт дубликат и не увеличивает `seq`.
- Два update с одной `base_version`: успешен только один.
- Конкурентные перемещения не создают цикл.
- Чужая категория в path возвращает `404`.
- Нельзя назначить чужого parent.
- Изменение сущности и journal entry всегда фиксируются вместе.

## Этап 3. Вещи

**Цель:** полный домен вещей, уже интегрированный с версионированием и синхронизацией.

### Задачи

- CRUD вещей.
- Typed item mutation applier для sync.
- Все поля из MVP:
  - категория;
  - название;
  - бренд;
  - описание;
  - год покупки;
  - цена и валюта;
  - место покупки;
  - состояние;
  - личная оценка;
  - дата последней носки;
  - место хранения;
  - сезон;
  - цвет;
  - размер;
  - статус;
  - архив.
- Архивирование и восстановление.
- Soft delete и tombstones.
- Поиск и фильтры.
- Подсказки мест хранения.
- Cursor pagination.

### Пагинация

Курсор должен содержать:

- значения полей сортировки;
- уникальный `id` как tie-breaker;
- fingerprint сортировки и фильтров.

При изменении фильтров старый курсор отклоняется. Сортировка выбирается только из allowlist, пользовательские SQL-фрагменты не принимаются.

### Валидация

- Цена без валюты — `422`.
- Валюта без цены — `422`.
- Отрицательная или дробная цена — `422`.
- Рейтинг вне диапазона 1–5 — `422`.
- Чужая или удалённая категория — `422 invalid_category`.
- Явный `null` корректно очищает необязательные поля.
- Неизвестные поля JSON отклоняются.

### Обязательные тесты

- Каждый CRUD создаёт ровно одно соответствующее журнальное изменение.
- Веб-изменения доступны через pull.
- Стабильная пагинация при одинаковых `updated_at`.
- Нельзя получить или изменить чужую вещь.
- Нельзя подставить чужую категорию.
- Конфликт версий возвращает `409`.
- Удаление создаёт tombstone.
- Создание и изменение вещей через sync используют ту же валидацию, что и веб.

## Этап 4. Фотографии

**Цель:** безопасная загрузка, обработка, приватное хранение и синхронизация metadata фотографий.

### Задачи

### Хранилище

- `PhotoStorage` interface.
- `LocalPhotoStorage`.
- Ключи формируются сервером.
- Пользовательское имя файла не участвует в пути.
- Листинг файлового каталога отключён.

### Загрузка

- `POST /api/v1/items/{itemId}/photos` для веба.
- `PUT /api/v1/items/{itemId}/photos/{photoId}/content` для мобильного клиента.
- Потоковая запись во временный файл.
- Лимит тела — 12 MiB.
- Поддерживается JPEG согласно MVP.
- Проверка содержимого, а не только расширения и MIME header.
- `DecodeConfig` до полного декодирования.
- Ограничения:
  - ширины;
  - высоты;
  - общего количества пикселей;
  - памяти обработки.
- Полное декодирование повреждённых данных должно завершаться ошибкой.
- Создание миниатюры с большей стороной около 512 px.

### Согласованность файлов и БД

Файловая система не участвует в SQL-транзакции, поэтому используется компенсирующий сценарий:

1. Загрузка и обработка во временном каталоге.
2. Сохранение подготовленных файлов.
3. SQL-транзакция:
   - обновление metadata;
   - перевод в `ready`;
   - увеличение `version`;
   - добавление journal entry.
4. При ошибке — очистка временных или осиротевших файлов.
5. Периодическая reconciliation-задача удаляет подтверждённые orphans.

Повтор `PUT content` с тем же `photo_id` идемпотентен. Изменение содержимого уже готового фото в MVP не поддерживается: создаётся новая фотография.

### Приватное скачивание

- Проверка владельца до открытия файла.
- Чужой `photo_id` возвращает `404`.
- Корректные `Content-Type`, `Cache-Control: private` и `X-Content-Type-Options: nosniff`.
- Original и thumbnail кэшируются клиентами раздельно.

### Порядок фотографий

Добавить:

```text
PUT /api/v1/items/{itemId}/photos/order
```

Запрос содержит полный порядок активных фотографий и `base_version` каждой фотографии.

Операция:

- атомарно проверяет весь набор;
- изменяет `sort_order`;
- увеличивает версии изменённых фотографий;
- добавляет соответствующие sync changes;
- обложкой считается фотография с минимальным `sort_order`.

### Обязательные тесты

- Upload больше 12 MiB.
- Не-JPEG и повреждённый JPEG.
- JPEG с чрезмерными размерами.
- Ошибка storage и последующая очистка.
- Повторная загрузка content.
- Отсутствие состояния `ready`, если файлы не сохранены.
- Чужой `item_id` или `photo_id`.
- Удаление и tombstone.
- Переупорядочивание с конфликтом версии.
- Изменение статуса `ready` появляется в pull.
- Ошибка обработки одной фотографии не меняет карточку вещи.

## Этап 5. Полный протокол синхронизации

**Цель:** завершить push/pull для всех сущностей, идемпотентность, зависимости, tombstones и конфликты.

Название задачи — **conflict detection and reporting**. Backend не выбирает версию за пользователя.

### Push

- До 100 mutations в пакете.
- Независимые результаты по каждой mutation.
- Typed payload decoding по `entity` и `operation`.
- Запрет передачи `map[string]any` глубоко в доменный слой.
- Canonical request hash на основе нормализованного typed request.
- Поддерживаемые результаты:
  - `applied`;
  - `duplicate`;
  - `conflict`;
  - `validation_error`;
  - `dependency_missing`;
  - `mutation_id_reused`.

Повторная доставка:

- тот же `mutation_id` и hash не создаёт новых изменений;
- другой payload с тем же ID отклоняется;
- `dependency_missing` не считается окончательно обработанной mutation;
- после появления зависимости клиент может повторить отправку;
- конфликт не изменяет серверную сущность и возвращает актуальный snapshot.

### Pull

- Записи упорядочены по `seq`.
- Используется выборка `limit + 1` для определения `has_more`.
- `next_since` соответствует последней возвращённой записи.
- При отсутствии изменений `next_since` остаётся равным `since`.
- Поддерживаются полные snapshots и tombstones.
- Начальная синхронизация выполняется с `since=0`.
- `updated_at` не используется как курсор.

### Конфликты и удаления

- Update/update — `conflict` с текущим snapshot.
- Update/delete — конфликт без автоматического восстановления.
- Delete/delete — идемпотентный успех при соблюдении правил владельца.
- Create с уже существующим entity ID не перезаписывает сущность.
- Изменение категории проверяет циклы и зависимости.
- Metadata и статусы фотографий синхронизируются без передачи содержимого в JSON.

### Retention

В MVP:

- `sync_changes` не очищаются по возрасту;
- tombstones сохраняются;
- `processed_mutations` сохраняются;
- device-aware compaction отсутствует.

### Обязательные сценарии

1. Потерян HTTP-ответ после commit, клиент повторяет mutation.
2. Одинаковый `mutation_id` с другим payload.
3. Два устройства изменяют одну сущность.
4. Два устройства изменяют разные сущности.
5. Веб-изменение появляется в pull.
6. Pull несколькими страницами при параллельных записях.
7. Retryable dependency для вещи и категории.
8. Create/update/delete фотографий.
9. Tombstone доходит на второе устройство.
10. Пользователь B не может выполнить push или pull данных A.
11. Полная синхронизация нового устройства с `since=0`.
12. Повторная обработка не создаёт дополнительные `version` и `seq`.
13. Конфликт не блокирует независимые mutations.
14. Нарушение доменной валидации через sync невозможно.

## Этап 6. Production hardening и эксплуатационная готовность

**Цель:** подготовить backend к стабильной эксплуатации в Docker.

### HTTP и завершение работы

- Request ID middleware.
- JSON access logs:
  - route template;
  - status;
  - duration;
  - внутренний `user_id`;
  - `request_id`.
- Без тел запросов, токенов, паролей и signed URLs в логах.
- Server timeouts с учётом uploads и downloads.
- Отдельные body limits для JSON и фотографий.
- Graceful shutdown в `cmd/server/main.go`:
  - остановка приёма соединений;
  - ограниченное ожидание активных запросов;
  - остановка фоновых задач;
  - закрытие DB pool.

### Docker и production Compose

- Non-root runtime user.
- Миграции запускаются отдельной one-off задачей до переключения API.
- Caddy, API и PostgreSQL.
- PostgreSQL без публично опубликованного порта.
- Volumes:
  - PostgreSQL;
  - фотографии;
  - Caddy.
- Healthchecks и restart policy.
- Явная конфигурация trusted proxies.
- Секреты только через env/secrets, не в Git.

### Проверки качества

- `go test ./...`;
- `go test -race ./...`;
- `go vet ./...`;
- `golangci-lint run`;
- `govulncheck ./...`;
- миграции `Up → Down → Up`;
- sqlc generation diff;
- OpenAPI validation;
- интеграционные тесты против реального PostgreSQL.

### Backup и восстановление

- Backup PostgreSQL.
- Backup файлового хранилища.
- Контроль согласованности двух копий.
- Тестовое восстановление на чистом окружении.
- Проверка отсутствия потерянных metadata и фотографий.
- Runbook для миграций, отката API и восстановления.

Backend считается release candidate после прохождения тестов. Полный production release допускается только после проверки backup/restore.

## 6. Зависимости между этапами

```text
Этап 0 — инфраструктура и тестовый контур
   │
   ▼
Этап 1 — identity, сессии, user_sync_state
   │
   ▼
Этап 2 — change journal, категории, первый push/pull
   │
   ▼
Этап 3 — вещи на едином versioned write path
   │
   ▼
Этап 4 — фотографии и журналируемые metadata
   │
   ▼
Этап 5 — полный sync, зависимости, конфликты, tombstones
   │
   ▼
Этап 6 — production hardening
```

Дополнительные зависимости:

- Этап 2 зависит от пользователей и `user_sync_state`.
- Этап 3 зависит от категорий и journal.
- Этап 4 зависит от вещей и journal.
- Этап 5 не создаёт журнал «с нуля», а завершает уже используемый протокол.
- Базовые security-меры и тесты не откладываются до этапа 6.

## 8. Что не входит в backend-план

- Web-клиент на HTML/CSS/TypeScript с Vite.
- React Native/Expo mobile-клиент.
- Полные Playwright и мобильные E2E.
- S3-реализация `PhotoStorage`.
- Prometheus и внешняя APM-система.
- Redis, Kafka, Kubernetes и микросервисы.
- Автоматическая отправка email.
- CRDT и автоматическое объединение конфликтов.
- Device-aware compaction sync history.

При этом backend API и интеграционные тесты должны быть готовы к подключению обоих клиентов без изменения доменной модели.

## 9. Итоговый Definition of Done

Backend MVP считается готовым, когда:

1. Регистрация работает только по валидному одноразовому приглашению.
2. Recovery полностью завершается через API и отзывает старые сессии.
3. Данные пользователей строго изолированы.
4. Каждый CRUD категории, вещи и фотографий версионируется и журналируется атомарно.
5. Веб-изменения доступны мобильным клиентам через pull.
6. Повторная mutation не создаёт дубликатов.
7. Конфликты не приводят к молчаливой перезаписи данных.
8. Pull корректно работает с пагинацией и параллельными записями.
9. Tombstones и начальная синхронизация с `since=0` поддерживаются.
10. Загрузка фотографий защищена от oversized и malformed input.
11. Файлы и metadata не остаются в ложном состоянии `ready`.
12. Все интеграционные, конкурентные и failure-тесты проходят.
13. Миграции проверены в обе стороны.
14. Docker deployment, graceful shutdown и логирование проверены.
15. Backup и восстановление PostgreSQL вместе с фотографиями проверены практически.
