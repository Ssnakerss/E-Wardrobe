# Wardrobe — требования и пошаговый план MVP

Статус: baseline v0.1  
Назначение: зафиксировать объём первой production-версии и критерии её готовности.

## 1. Цель продукта

Система помогает пользователю помнить, какие личные вещи у него есть, где они хранятся и в каком состоянии находятся.

Основной сценарий:

1. Пользователь фотографирует вещь на телефон.
2. Добавляет название, категорию и необязательные характеристики.
3. Сохраняет вещь даже без подключения к сети.
4. Позже находит её через поиск, категории и фильтры.
5. После синхронизации видит те же данные в веб-клиенте и на других устройствах.

## 2. Участники

- Пользователь — владелец своего гардероба.
- Оператор установки — администрирует Docker-окружение и создаёт приглашения через CLI.

Отдельной роли администратора внутри веб-приложения в MVP нет.

## 3. Платформы и компоненты

- Мобильное приложение: React Native, Expo, TypeScript, Android и iOS.
- Локальная мобильная БД: SQLite.
- Backend: Go, модульный монолит.
- Основная БД: PostgreSQL.
- Веб-клиент: HTML, CSS, TypeScript без UI-фреймворка.
- Веб-сборка встраивается в Go-бинарник и раздаётся backend.
- Фотографии: файловое хранилище на Docker volume за абстракцией PhotoStorage.
- Развёртывание: Docker Compose, Caddy, API и PostgreSQL.

Веб-клиент является полноценным онлайн-клиентом. Offline-first реализуется на мобильном приложении.

## 4. Регистрация и доступ

Регистрация возможна только по одноразовому приглашению.

Требования:

- Приглашение создаётся командой оператора.
- Ссылка может быть передана пользователю вручную.
- SMTP и отправка email в MVP не требуются.
- Срок действия приглашения по умолчанию — 7 суток.
- Приглашение может быть привязано к email.
- В базе хранится только хеш токена приглашения.
- Использованное, просроченное или отозванное приглашение не принимается.
- Регистрация и погашение приглашения происходят в одной транзакции.
- После регистрации пользователю копируется базовый справочник категорий.
- Повторное использование ссылки запрещено.
- Вход, регистрация и проверка приглашения защищаются rate limiting.

Пример команды:

    docker compose exec api wardrobe invite create \
      --email user@example.com \
      --expires 168h

Доступ к данным:

- Пользователь видит только свои категории, вещи и фотографии.
- Проверка владельца выполняется на backend для каждого запроса.
- Знание UUID чужой сущности не даёт доступа к ней.
- URL фотографий не являются публичными.

## 5. Аутентификация

Используются серверные сессии с непрозрачными случайными токенами.

Веб:

- Session ID передаётся в HttpOnly Secure cookie.
- SameSite и проверка Origin ограничивают межсайтовые запросы.
- Изменяющие запросы дополнительно защищаются CSRF-токеном.
- JavaScript не получает серверный session token.

Мобильное приложение:

- Получает Bearer token после входа или регистрации.
- Хранит его в iOS Keychain или Android Keystore через Secure Store.
- Истечение серверной сессии не блокирует доступ к локальной SQLite БД.
- После повторной аутентификации можно продолжить синхронизацию.

Пароли хешируются Argon2id. Восстановление доступа в MVP выполняется через одноразовую recovery-ссылку, созданную оператором через CLI. Автоматическая отправка писем не входит в объём.

## 6. Категории

Категории образуют дерево произвольной разумной глубины.

Пример базового шаблона:

    Одежда
      Верхняя одежда
      Футболки
        Спортивные
      Брюки
      Нижнее бельё
    Обувь
      Зимняя
      Летняя
      Спортивная
    Аксессуары
    Прочее

Правила:

- Базовый шаблон хранится в backend.
- При регистрации шаблон копируется в категории пользователя.
- template_key сохраняет связь с исходным элементом шаблона.
- После копирования категории принадлежат пользователю и синхронизируются обычным образом.
- Пользователь может создавать, переименовывать, перемещать и архивировать категории.
- Перемещение не должно создавать цикл.
- Родительская категория должна принадлежать тому же пользователю.
- Нельзя окончательно удалить категорию, если на неё ссылаются активные вещи или дочерние категории.
- В такой ситуации предлагается архивирование либо предварительное перемещение вещей.

## 7. Карточка вещи

| Поле | Обязательность | Правила |
|---|---|---|
| id | Системное | UUID, может быть создан на мобильном устройстве |
| name | Да | От 1 до 200 символов после trim |
| category_id | Да | Категория того же пользователя |
| brand | Нет | До 200 символов |
| description | Нет | Свободный текст |
| purchase_year | Нет | Год покупки, разумный диапазон проверяется на backend |
| purchase_price | Нет | Целое неотрицательное число |
| price_currency | Нет | ISO 4217, обязательна при указанной цене |
| purchase_place | Нет | Магазин, маркетплейс или другое место покупки |
| condition_rating | Нет | Целая оценка от 1 до 5 |
| preference_rating | Нет | Насколько вещь нравится, от 1 до 5 |
| last_worn_on | Нет | Дата без времени |
| storage_location | Нет | Свободный текст с автоподсказками |
| season | Нет | Зима, весна, лето, осень, демисезон, всесезонная |
| color | Нет | Текст |
| size | Нет | Текст, поскольку размерные сетки различаются |
| status | Да | in_use, stored или needs_repair |
| archived_at | Системное | Признак нахождения в архиве |
| version | Системное | Серверная версия для синхронизации |
| created_at, updated_at | Системное | UTC |

### Стоимость

Стоимость хранится в целых основных единицах валюты:

- 12990 и RUB означают 12990 рублей.
- 120 и USD означают 120 долларов.
- Дробная часть не поддерживается.
- Копейки, центы и другие минорные единицы не хранятся.
- Отрицательные значения запрещены.
- Цена и валюта либо заполнены вместе, либо обе отсутствуют.
- По умолчанию интерфейс предлагает RUB.
- Начальный список выбора: RUB, USD, EUR, KZT, CNY.
- Пересчёт курсов и суммарная стоимость гардероба в одной валюте не реализуются.

В JSON цена передаётся строкой:

    {
      "purchase_price": "12990",
      "price_currency": "RUB"
    }

Это исключает проблемы с 64-битными целыми и числами JavaScript.

### Место хранения

Хранится как текст, а не как отдельный справочник.

Примеры:

- Дома, спальня, верхняя полка.
- Дача, гардероб.
- Кладовка, коробка «Зимняя обувь».

При сохранении обрезаются внешние пробелы и схлопываются повторные пробелы. Пустая строка превращается в NULL.

Мобильные подсказки строятся по локальным вещам и работают офлайн. Веб получает подсказки через отдельный endpoint. Подсказки доступны только в пределах текущего пользователя.

## 8. Фотографии

Требования MVP:

- Несколько фотографий на одну вещь, начальный лимит — 10.
- Камера и галерея на мобильном устройстве.
- Загрузка файла в веб-клиенте.
- Порядок фотографий и выбор обложки через первое фото в списке.
- Миниатюра для списков и полноразмерное изображение для карточки.
- Локальный файл доступен на телефоне сразу после добавления.
- Карточка вещи не зависит от успешной загрузки фотографии.

Обработка:

- Мобильное приложение нормализует изображение в JPEG.
- Учитывается EXIF-ориентация.
- Большая сторона уменьшается максимум до 2560 пикселей.
- EXIF с геолокацией не отправляется.
- Backend проверяет размер, формат и фактическое содержимое.
- Предельный размер исходного upload в MVP — 12 MiB.
- Backend создаёт миниатюру с большей стороной около 512 пикселей.
- Пользовательское имя файла не используется как ключ хранения.
- Декодирование изображений имеет ограничение по размерам и памяти.

Состояния фотографии:

- local_only — существует только на устройстве.
- awaiting_upload — metadata принята сервером, файл ещё не загружен.
- uploading — идёт передача содержимого.
- processing — сервер создаёт миниатюру.
- ready — файл и миниатюра готовы.
- failed — ошибка, доступен повтор.

## 9. Списки, поиск и фильтры

Веб и мобильный клиент поддерживают:

- Карточки с обложкой, названием, брендом и категорией.
- Навигацию по дереву категорий.
- Фильтр по выбранной категории с учётом вложенных категорий.
- Поиск по названию, бренду и описанию.
- Фильтры по сезону, состоянию, личной оценке и статусу.
- Отдельный просмотр архива.
- Сортировку по дате добавления, дате изменения, названию и году покупки.
- Пагинацию серверного списка.
- Индикаторы несинхронизированных изменений на мобильном устройстве.

Дополнительные удобства:

- Быстрая отметка «носил сегодня».
- Быстрое изменение места хранения.
- Отображение времени последней успешной синхронизации.
- Повтор синхронизации после ошибки.

## 10. Offline-first

Мобильный UI читает и изменяет только SQLite. Экраны не зависят от прямого ответа REST API.

Гарантии:

- Создание и редактирование работают без сети.
- Фотографии сохраняются в постоянном каталоге приложения.
- Данные и outbox записываются атомарно.
- Закрытие или перезапуск приложения не удаляет очередь.
- Повтор mutation не создаёт дубликаты.
- Конфликт не приводит к молчаливой потере локальной версии.
- Ошибка одной операции не останавливает независимые операции.
- Выход из аккаунта предупреждает о несинхронизированных данных.

Синхронизация запускается:

- При открытии приложения.
- При возвращении в foreground.
- После локального изменения при наличии сети.
- После восстановления соединения.
- Вручную.
- В фоне только как best effort.

Гарантированная доставка изменений после сворачивания приложения не обещается.

Подробный протокол описан в docs/sync.md.

## 11. Экраны

### Общие

- Проверка и регистрация по приглашению.
- Вход.
- Ошибка недоступности сервера для онлайн-операций.

### Веб

- Список вещей: карточки и таблица.
- Дерево категорий.
- Карточка вещи.
- Форма создания и редактирования.
- Управление фотографиями.
- Архив.
- Выход из аккаунта.

### Мобильное приложение

- Локальный список вещей.
- Категории и фильтры.
- Карточка вещи.
- Создание и редактирование без сети.
- Добавление фотографий.
- Состояние синхронизации.
- Список конфликтов.
- Экран сравнения локальной и серверной версий.

## 12. Нефункциональные требования

- Все серверные timestamps хранятся как timestamptz в UTC.
- Дата последней носки хранится как date.
- Все внешние запросы имеют timeout.
- Изменяющие HTTP-запросы не должны зависать при недоступном файловом хранилище.
- Backend запускается одним экземпляром.
- Миграции запускаются до переключения на новую версию backend.
- Логи не содержат пароли, токены, приглашения и содержимое фотографий.
- Бэкап включает PostgreSQL и файлы фотографий.
- Перед релизом выполняется тестовое восстановление.
- Списки не загружают полный гардероб одним HTTP-запросом.
- Мобильный список использует локальную пагинацию или виртуализацию.

## 13. Что не входит в MVP

- Открытая самостоятельная регистрация.
- Полноценная offline-версия веб-клиента.
- Подтверждение email и автоматическая отправка писем.
- Социальный вход.
- Подбор образов и комплектов.
- История каждой носки; хранится только последняя дата.
- Напоминания о стирке и химчистке.
- Распознавание одежды через ИИ.
- Публичные гардеробы и совместный доступ.
- Курсы валют и конвертация.
- Иерархический справочник мест хранения.
- S3, Redis, очередь сообщений и микросервисы.
- Гарантированная фоновая синхронизация мобильных ОС.

## 14. Пошаговый план реализации

### Шаг 0. Подготовка репозитория

Задачи:

- Создать monorepo.
- Добавить README, Makefile, .editorconfig и .env.example.
- Зафиксировать требования в docs/mvp.md.
- Зафиксировать архитектуру и протокол синхронизации.
- Настроить форматирование и базовый CI.

Результат:

- Документы доступны в репозитории.
- Структура проектов backend, web и mobile согласована.

### Шаг 1. Development-инфраструктура

Задачи:

- Поднять PostgreSQL в Docker Compose.
- Подключить goose и миграции.
- Создать минимальный Go server.
- Добавить конфигурацию через переменные окружения.
- Добавить /health/live и /health/ready.
- Настроить структурные логи slog.

Критерий готовности:

- Чистое окружение поднимается документированной командой.
- Миграции применяются повторяемо.
- Ready endpoint проверяет доступность PostgreSQL.

### Шаг 2. Пользователи и приглашения

Задачи:

- Реализовать invite create/revoke CLI.
- Реализовать проверку приглашения и регистрацию.
- Добавить Argon2id и серверные сессии.
- Реализовать cookie и Bearer transports.
- Добавить logout и auth middleware.
- Копировать базовые категории при регистрации.
- Добавить rate limiting.

Тесты:

- Просроченное и повторно использованное приглашение отклоняется.
- Два параллельных запроса не могут использовать одно приглашение дважды.
- Email приводится к каноническому виду.
- Пользователь не получает чужие данные.

### Шаг 3. Домен вещей и категорий

Задачи:

- Реализовать repository и domain service поверх sqlc/pgx.
- Добавить CRUD категорий.
- Проверять циклы и владельца родителя.
- Добавить CRUD вещей со всеми полями.
- Добавить архивирование и soft delete.
- Добавить фильтры, сортировку и cursor pagination.
- Добавить endpoint подсказок мест хранения.

Тесты:

- Нельзя указать чужую категорию.
- Цена без валюты отклоняется.
- Дробная и отрицательная цена отклоняется.
- Оценки вне диапазона от 1 до 5 отклоняются.
- Категория не может стать потомком самой себя.

### Шаг 4. Серверная основа синхронизации

Задачи:

- Вести version для категорий, вещей и фотографий.
- Вести per-user sync sequence.
- Записывать полные snapshots в sync_changes.
- Реализовать идемпотентный push.
- Реализовать pull с пагинацией.
- Проверять base_version.
- Возвращать conflict вместе с актуальным snapshot.
- Пропускать веб CRUD через тот же domain service.

Тесты:

- Повтор mutation_id возвращает сохранённый результат.
- Повторное использование mutation_id с другим содержимым отклоняется.
- Изменения получают строго возрастающий seq.
- Pull не пропускает изменения между страницами.
- Несовпавшая base_version не перезаписывает серверные данные.

### Шаг 5. Минимальный веб-клиент

Задачи:

- Настроить TypeScript и Vite.
- Сгенерировать API types из OpenAPI.
- Реализовать регистрацию и вход.
- Реализовать список, карточку и форму вещи.
- Реализовать категории, фильтры и архив.
- Встроить production build в Go через go:embed.

Критерий готовности:

- Пользователь управляет гардеробом из браузера без мобильного приложения.
- Node.js не требуется в production-контейнере.

### Шаг 6. Локальное мобильное приложение

Задачи:

- Создать Expo/React Native проект.
- Реализовать миграции SQLite.
- Создать repositories для категорий и вещей.
- Реализовать локальные экраны списка и редактирования.
- Добавить outbox в той же SQLite-транзакции.
- Хранить session token в Secure Store.
- Разделить локальные данные по user_id.

Критерий готовности:

- В авиарежиме можно создать категорию и вещь.
- После полного перезапуска приложения данные остаются.
- UI не показывает сетевую ошибку при локальном сохранении.

### Шаг 7. Вертикальный срез синхронизации

Задачи:

- Реализовать Sync Engine с single-flight блокировкой.
- Добавить compaction outbox.
- Реализовать push/pull цикл.
- Сохранять last_pulled_seq атомарно с применением изменений.
- Добавить ручную синхронизацию и индикаторы состояния.
- Реализовать повтор после сетевых ошибок.

Приёмочный сценарий:

- Вещь создана на телефоне без сети.
- Вещь появляется в вебе после восстановления сети.
- Изменение в вебе возвращается на телефон.
- Повторная отправка не создаёт дубликат.

### Шаг 8. Фотографии

Задачи:

- Добавить выбор изображения и съёмку.
- Копировать исходник в постоянное локальное хранилище.
- Нормализовать и уменьшать изображение.
- Реализовать metadata sync и отдельную очередь content upload.
- Реализовать серверную проверку и создание миниатюр.
- Реализовать скачивание и кэширование фотографий.
- Добавить повтор загрузки и отмену ещё не отправленного фото.

Критерий готовности:

- Офлайн-фотография переживает перезапуск.
- Ошибка загрузки фото не удаляет вещь.
- Готовая фотография появляется на втором клиенте.

### Шаг 9. Конфликты и удаления

Задачи:

- Реализовать экран сравнения версий.
- Добавить выбор серверной или локальной версии.
- Передавать tombstones при удалении.
- Обрабатывать update-versus-delete.
- Не перезаписывать локально изменённую сущность во время pull.
- Добавить category_in_use и dependency_missing.

Критерий готовности:

- Ни один конфликт не приводит к молчаливой потере локальной версии.
- Удаление распространяется на другие устройства.

### Шаг 10. UX и производительность

### Шаг 12. Релиз

Обязательные проверки:

- Регистрация работает только по валидному приглашению.
- Пользователь A не получает данные пользователя B.
- Офлайн-данные переживают перезапуск и обновление приложения.
- Конфликты решаются явно.
- Веб и мобильный клиент используют одну серверную модель.
- Backup восстанавливается на чистом окружении.
- Миграции и rollback deployment описаны в runbook.

## 15. Definition of Done

MVP считается готовым, когда:

1. Оператор может создать приглашение без доступа к SQL.
2. Пользователь может зарегистрироваться и войти на двух клиентах.
3. Гардеробом можно полноценно управлять из веба.
4. На телефоне можно работать без сети.
5. Синхронизация идемпотентна и не теряет outbox.
6. Конфликт отображается пользователю.
7. Фотографии синхронизируются отдельно и восстанавливаются после ошибок.
8. Цена и валюта соответствуют принятой модели целых единиц.
9. Место хранения имеет автоподсказки.
10. Развёртывание и восстановление из backup проверены на практике.
